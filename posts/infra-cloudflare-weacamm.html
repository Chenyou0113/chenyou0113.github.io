從零調整 weacamm.org：網域基礎設施與 Cloudflare 的日常微調

DNS、SSL/TLS、Page Rules，還有那些文件沒寫但會咬人的細節。這篇記下我把 weacamm.org 的基礎設施重新整理一輪的過程。

目錄

  1. 為什麼自己管
  2. DNS：先把地基看清楚
  3. SSL/TLS 與那些「應該會自動好」的事
  4. Page Rules 與快取
  5. 還沒做的

為什麼自己管

把網域交給代管商最省事，但也就沒辦法知道中間發生了什麼。 有一次子網域突然連不上，查了半天才發現是憑證自動續期失敗， 而代管商的介面只寫著「正常」。從那次之後，我決定把 DNS 與憑證都收到自己手上。

現在 weacamm.org 的 DNS 放在 Cloudflare，主要服務跑在 Workers 與 Pages 上。 好處是每一層都能看到，壞處是每一層都要自己顧。

DNS：先把地基看清楚

第一件事是把所有記錄列出來，一條一條確認用途。整理完才發現：

  • 有幾條 A 記錄指向已經不在使用的舊主機
  • 同一組子網域同時存在 CNAME 與 A，行為取決於查詢順序
  • 有一條 TXT 是幾年前驗證用的，早就過期

這些記錄不會讓網站掛掉，但會讓除錯變得很痛苦。清掉之後，整份 DNS 表單只剩十幾條， 每一條都說得出為什麼存在。

基礎設施的問題通常不是「壞了」，是「有東西存在但沒人知道它為什麼存在」。

我把代理狀態（橘色雲朵）也重新確認了一次。需要讓 Cloudflare 處理 TLS 與快取的走代理， 純粹做郵件驗證或外部服務驗證的就直接 DNS only。

SSL/TLS 與那些「應該會自動好」的事

Cloudflare 的 Universal SSL 會自動簽發邊緣憑證，這部分通常不用管。 真正會出事的是來源伺服器那一端。

如果你的來源只有 HTTP，而 Cloudflare 的 SSL 模式設成「Full」， 就會出現無限重導或 525。我踩過一次，症狀是瀏覽器顯示「重新導向次數過多」， 但 Cloudflare 的儀表板看起來一切正常。

後來的設定是：

項目設定原因
SSL 模式Full (strict)來源也要有有效憑證，避免中間被攔
Always Use HTTPS開啟避免明文請求
Automatic HTTPS Rewrites開啟補救頁面內的 http:// 資源
Minimum TLS Version1.2相容性與安全性的折衷

「Full (strict)」比「Full」多一道驗證，代價是來源伺服器必須有有效憑證。 如果來源是 Workers 或 Pages，這道自動滿足；如果是自己的機器，就得自己想辦法續期。

Page Rules 與快取

快取規則是我花最多時間的地方。預設行為是「能快取就快取」， 但對即時資料來說，這個預設是錯的。

以 weacamm.org 上的交通資料為例，公車動態每幾十秒就變一次， CCTV 畫面更是每秒都在更新。這些路徑如果被快取住，使用者看到的就是過期畫面。 

// 即時資料：不快取，直接回源
example.com/api/rt/*
  Cache Level: Bypass

// 靜態資源：長期快取
example.com/assets/*
  Cache Level: Cache Everything
  Edge Cache TTL: a month

另外把 Cache-Control 的決定權交回給來源。 Workers 回應時可以自己指定 max-age， 這比在 Cloudflare 介面上猜規則準確得多。

要注意的是 Page Rules 有數量上限（免費方案是三條）。 規則一多就會打架，順序也會影響結果。我的做法是：能在程式裡決定的，就不要寫成規則。

還沒做的

整理到現在，還有幾件事擱著：

  • DNSSEC——知道該開，但還沒實際操作過，怕弄壞解析。
  • 日誌保存——免費方案的日誌保留時間很短，長期分析要另外想辦法。
  • 監控——目前是靠「有人回報才知道掛了」，應該加個 uptime 檢查。

基礎設施這種東西，做完當下最有感，過一陣子就會忘記當初為什麼這樣設。 所以趁還記得的時候寫下來，下次要改的時候至少知道從哪裡開始看。
