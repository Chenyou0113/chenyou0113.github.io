鐵道旅行與時刻資料：日常交通觀察的數位實踐

從月台上的一張時刻表，到電腦裡的一份 JSON。這篇寫我怎麼把「喜歡搭火車」和「寫程式」這兩件事接在一起。

目錄

  1. 起點：月台上的那張表
  2. 時刻表的資料長什麼樣子
  3. 旅行中的數位實踐
  4. 為什麼這件事值得做

起點：月台上的那張表

花蓮站的月台上有一張很大的時刻表。印刷的，不是螢幕。 上面用不同顏色標示車種，密密麻麻排著一整天往台北、往台東的班次。

有一次我在那裡等車，盯著那張表看了十分鐘，忽然發現一件事： 我其實不是在看「下一班車什麼時候來」，而是在看這條路線一整天的節奏。 早上七點到九點是一段，中午空下來，傍晚又密起來。

這種「節奏」在手機 App 裡看不到。App 只會告訴你最近的一班，因為它假設你很急。 但如果你不趕時間，整張表透露的資訊其實多得多。

時刻表的資料長什麼樣子

後來我開始去看交通部釋出的開放資料。以軌道運輸為例， 一份「每日時刻表」的資料大概長這樣（簡化過）： 

{
  "TrainNo": "408",
  "TrainType": "自強(3000)",
  "StartingStationID": "7000",
  "EndingStationID": "0900",
  "StopTimes": [
    {
      "StationID": "7000",
      "ArrivalTime": "06:30",
      "DepartureTime": "06:30"
    },
    {
      "StationID": "6000",
      "ArrivalTime": "07:45",
      "DepartureTime": "07:47"
    }
  ]
}

看起來很簡單，但實際處理會遇到幾個問題：

  • 時間格式不統一——有些是 HH:mm，有些是 HH:mm:ss，跨日還要用 24:10 這種寫法。
  • 站名與站碼的對應——同一份資料裡可能同時出現站名、站碼與舊站碼。
  • 車種代碼——自強、莒光、區間的命名在不同資料集裡不一致。
  • 臨時列車——加開的班次不會出現在固定時刻表裡，要另外抓。

真正麻煩的從來不是「讀取 JSON」，是「理解這份 JSON 到底在說什麼」。 每個欄位的定義都要去翻規格文件，而且文件常常比資料本身還晚更新。

開放資料的價值不在資料本身，而在有人願意花時間把它整理成能用的樣子。

旅行中的數位實踐

我後來養成一個習慣：出發前把當天的班次抓下來，存成一份離線檔案。 原因很實際——有些路段收訊不好，有些時候我只是想快速翻閱，不想一直重新查詢。

這份離線檔案後來變成一個小工具的基礎。它可以：

  • 輸入起訖站，列出當天所有可行組合
  • 標出轉乘時間太短的組合（避免趕不上）
  • 顯示每個班次的車種與行駛時間

寫這個工具花了我大概三個週末。用起來有沒有比較快？老實說沒有。 但它讓我真正理解時刻表是怎麼組成的——這件事本身的價值超過工具。

為什麼這件事值得做

有人問我「你幹嘛不直接查 App」。這問題很好，我認真想過。

App 給的是答案：下一班 18:42，第 3 月台。 我想要的是脈絡：為什麼是 18:42、為什麼中間隔了 47 分鐘、這段時間車去哪裡了。

把時刻表拆開來看，會發現很多設計上的選擇。 為什麼某個班次停的站比較少？為什麼某段時間完全沒有車？ 這些問題的答案通常不在程式裡，在排班表的人的考量裡。

而我寫程式，有一部分就是為了看懂這些考量。 程式不只是寫扣，它也是理解這個世界運作方式的一種工具。

下次你站在月台上，可以試著看一下那張表。 不是看下一班車，是看一整天。
