把 30 秒輪詢改成看得見才抓：一次 TDX 看板的省電改版

手機放著不動也在燒電，問題出在輪詢策略而不是資料量。這篇記下改版前後的數字，還有中間試錯的過程。

目錄

  1. 問題：不動也在耗電
  2. 先量，再改
  3. 三層策略
  4. 結果與還沒解的

問題：不動也在耗電

看板上線之後收到一個回報：手機放進口袋，兩個小時後電量掉了 18%。 那頁只有一張地圖和十幾台公車的動態，照理說不該這麼兇。

打開 DevTools 看 Network，答案很明顯：每 30 秒一次 /api/bus， 一次抓全台。而且分頁切到背景、手機螢幕關掉，它照樣在打。 

setInterval(fetchAll, 30000);

這行是當初五分鐘寫完的，能動，但從來沒想過「什麼時候不需要抓」。

先量，再改

我沒有立刻改程式，先加了三個計數器，跑了一週：

  • 每小時的請求次數
  • 每次回應的位元組大小
  • 使用者實際盯著看板的分鐘數

結果是：平均每個工作階段 22 分鐘，但請求量相當於盯著看 4 小時。 也就是說 八成以上的請求，是在沒人看畫面的時候發生的。

直覺會以為要「減少資料量」，但真正的浪費是「在不必要的時候抓」。

三層策略

最後定下三種狀態，各自有不同的節奏：

狀態判斷方式輪詢間隔
可見且聚焦visibilityState === 'visible' 且有 focus15 秒
可見但失焦分頁在前景，但視窗沒 focus60 秒
背景分頁隱藏或螢幕關閉不抓

另外把「全台一次抓」改成依目前地圖視窗（bounding box）只抓看得到的路線。 這一步砍掉的資料量比調整間隔還多。 

document.addEventListener('visibilitychange', () => {
  if (document.hidden) {
    stopPolling();
  } else {
    pollNow();
    startPolling();
  }
});

要注意的是：回到前景時不能只重啟計時器，要立刻抓一次， 不然使用者會看著 30 秒前的舊資料。

結果與還沒解的

改版後一週，同樣的 22 分鐘使用時間，請求數從大約 2,600 次降到 190 次。 回報耗電的那位說「現在放口袋不會熱了」。

還沒解的問題有兩個：

  • 手機鎖屏後 JS 會被凍結，回到前景時計時器行為不一致，目前是靠 visibilitychange 補救，但 iOS Safari 偶爾還是會漏。
  • 離峰時段（深夜）其實可以更省，但差別已經小到不值得再複雜化。

這次學到的是：效能問題常常不是「程式寫得不好」，是「沒有問過什麼時候不該做事」。
