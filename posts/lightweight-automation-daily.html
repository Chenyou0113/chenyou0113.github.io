給生活加一點自動化：用輕量工具解決日常瑣事

不求龐大系統，只用最精簡的腳本，把重複的事交給機器。這篇列出我目前有在跑的自動化，以及為什麼大部分都刻意保持很小。

目錄

  1. 先找出「每次都卡一下」的地方
  2. 三個目前有在跑的例子
  3. 刻意保持很小的理由
  4. 自動化的哲學

先找出「每次都卡一下」的地方

自動化最容易失敗的方式，是一開始就想做一個大系統。 我試過兩次，兩次都做到一半就停擺——因為需求還沒穩定，系統就先變複雜了。

後來換一個方法：不先想「可以做什麼自動化」，而是記錄「這週有哪些事讓我卡了一下」。 連續記兩週，會發現重複出現的就那幾件。

  • 每次改完東西，要手動確認某個頁面還活著
  • 某些資料要定期抓下來，但常常忘記
  • 檔案散在不同地方，每次要找都要重新想一次在哪

這些事單獨看都很小，但累積起來會吃掉專注力。而專注力比時間更難恢復。

三個目前有在跑的例子

1. 定時檢查與通知

有些服務掛掉不會自己通知你。我目前的做法是用 GitHub Actions 的排程， 定時打一個檢查的請求，失敗就寄信。整個流程就是一個 YAML 檔加幾行腳本。 

name: uptime-check

on:
  schedule:
    - cron: '0 */6 * * *'
  workflow_dispatch:

jobs:
  ping:
    runs-on: ubuntu-latest
    steps:
      - name: Check endpoint
        run: |
          code=$(curl -s -o /dev/null -w "%{http_code}" https://example.com/)
          echo "status: $code"
          [ "$code" = "200" ] || exit 1

沒有監控服務、沒有資料庫、沒有儀表板。掛掉的時候我知道，這樣就夠了。

2. 資料的定期快照

開放資料會改版。某個欄位今天叫 A，明年可能叫 B。 為了在改版時還原得回去，我會定期把原始資料存一份。

這件事用 Actions 做也很合適：抓資料、壓縮、放進 repo 或物件儲存。 要注意的是不要讓 repo 無限長大——我只保留最近幾份，舊的直接覆蓋。

3. 重複的檔案整理

這類工作我用本機的 Python 腳本處理，沒有放到雲端。 原因很簡單：檔案在本機，多傳一趟只是增加出錯的機會。 

from pathlib import Path
import shutil

src = Path.home() / "Downloads"
dst = Path.home() / "Documents" / "inbox"

for f in src.glob("*.pdf"):
    target = dst / f.name
    if target.exists():
        continue
    shutil.move(str(f), str(target))

這段程式很短，但它每天幫我省下一個「打開下載資料夾、判斷、拖曳」的動作。 大概十秒。一年下來是將近一小時，而且是不用動腦的一小時。

刻意保持很小的理由

我對自動化有一條規則：如果它壞掉，我能在五分鐘內看懂為什麼。

這條規則排除了很多方案。用一個現成的自動化平台聽起來很方便， 但出問題時你要在別人的抽象層裡找原因。用一個自己寫的 30 行腳本， 出問題時你知道去哪裡看。

具體來說，我盡量遵守這幾件事：

  • 能用 cron + 一支腳本解決，就不要引入框架。
  • 每個自動化只做一件事。兩件事就寫兩個，不要合併。
  • 失敗要吵。安靜失敗的自動化比沒有自動化更糟。
  • 留下日誌。至少留下一行「什麼時候跑了、結果如何」。

自動化的哲學

有人覺得自動化是為了「效率」。我覺得不完全是。

把十秒的動作自動化，省的是一小時裡的一分鐘，效益其實很低。 真正的價值在別的地方：它讓你不用記得。

人腦適合思考，不適合記住「每週三要手動備份」這種事。 把這些事交給機器，不是為了快，是為了把注意力留給真正需要思考的部分。

花時間把流程寫好，是為了省下未來更多的專注力。

所以我的自動化清單一直不長。每次想加一個，我會先問： 這件事值得我花時間寫，而且以後不用再想它嗎？

如果答案是「好像也還好」，那就不做。 留下來的每一個，都是真的讓我少想一件事的。
