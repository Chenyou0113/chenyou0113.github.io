為什麼我把 CCTV 串流包了一層代理

直接嵌政府網站的 MJPEG 串流會遇到三個問題。這篇說明那三個問題，以及最後為什麼是用 Workers 而不是別的方案。

目錄

  1. 一開始想直接嵌
  2. 三個擋路的問題
  3. Workers 的角色
  4. 成本與限制

一開始想直接嵌

監控平台要放全台道路 CCTV。第一版很直覺：把政府提供的串流網址直接塞進 <img> 就好。 

<img src="https://example.gov.tw/cctv/12345.mjpg">

本機測試會動。部署到 GitHub Pages 之後，全部變成破圖。

三個擋路的問題

1. 跨域與防盜鏈

部分縣市的串流會檢查 Referer，只允許自家網域。 瀏覽器送出的 Referer 是 weacamm.org，於是被擋。 這個問題沒辦法用前端解，因為 Referer 是瀏覽器決定送什麼。

2. 只支援 HTTP

有些舊的攝影機只提供 http://。GitHub Pages 是 HTTPS， 瀏覽器會直接阻擋混合內容（mixed content）。這條沒有例外。

3. MJPEG 的連線數

一頁放 12 路 MJPEG，就是 12 條長連線同時開著。 這些連線不會結束，會一直佔用瀏覽器的並行連線額度， 導致同頁其他 API 請求被排隊。

不是「串流很慢」，是「串流佔住了其他東西的路」。這兩個問題的解法完全不同。

Workers 的角色

最後在 Cloudflare Workers 上寫了一個代理，做三件事：

  1. 代為加上正確的 Referer 與必要的 header，繞過防盜鏈
  2. 把 http:// 的來源轉成 HTTPS，解決混合內容
  3. 加上快取，短時間內重複請求直接回快取，降低來源負擔
export default {
  async fetch(request, env, ctx) {
    const url = new URL(request.url);
    const target = url.searchParams.get('src');
    if (!target) return new Response('missing src', { status: 400 });

    const upstream = await fetch(target, {
      headers: { 'Referer': 'https://www.example.gov.tw/' }
    });

    const headers = new Headers(upstream.headers);
    headers.set('Access-Control-Allow-Origin', '*');
    headers.set('Cache-Control', 'public, max-age=5');

    return new Response(upstream.body, {
      status: upstream.status,
      headers
    });
  }
};

選 Workers 的原因很單純：它在邊緣執行，離來源與使用者都近， 而且免費方案對這種低流量的代理很夠用。不用開機器、不用管憑證。

成本與限制

目前代理了大概 400 路攝影機，但同時在線最多十幾路。 Workers 免費方案的每日請求數對這個量來說綽綽有餘。

限制也很明確：

  • Workers 的執行時間有上限，不適合長時間的串流。所以只用於 MJPEG 的短連線與 HLS 的片段代理。
  • 快取時間必須短。CCTV 的意義就是即時，設太長會看到過期畫面。
  • 如果來源本身掛了，代理也只能回錯誤，不會變出畫面。

後來有讀者問為什麼不用現成的 CORS proxy。 原因是那些服務通常不保證可用性，也不適合拿來代理政府網站的流量。 自己包一層，至少掛掉的時候知道去哪裡看 log。
